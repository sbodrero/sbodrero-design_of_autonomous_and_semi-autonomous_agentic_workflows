1. Overview

The Warehouse Intelligence Assistant (WIA) is a single-agent AI system that helps warehouse operations managers make real-time, safety-aware fleet coordination decisions through natural language interaction. Given a request such as "Route AGV-3 to pick zone C — is the inventory sufficient and is the path clear?", the agent autonomously gathers context from simulated warehouse tools, reasons about safety constraints, and returns a concrete recommendation or escalates to a human supervisor when required.

The agentic approach is motivated by the multi-step, context-dependent nature of warehouse coordination queries. A static rule engine cannot handle the open-ended combination of vehicle availability checks, inventory queries, path computation, and dynamic safety constraints that a single manager request may require. An LLM-driven reasoning loop — where the model iteratively decides which tool to call next, integrates results across calls, and adapts its strategy when unexpected conditions arise — is the appropriate architectural pattern for this class of task (Wang et al., 2024).

The system is intentionally scoped for academic demonstration. All warehouse data is simulated via Python dictionaries; no live WMS API integration is required. The goal is to demonstrate the core agentic design pattern — tool-use reasoning, memory, safeguards, and ethical constraints — in a reproducible, portfolio-appropriate form.

2.4 Memory Design

The agent uses two distinct memory structures. Conversation history is a standard list of Claude API message dicts (alternating user/assistant/tool_result) that is rebuilt from scratch at each user turn. This keeps the context window bounded and avoids the token cost of carrying stale multi-turn context. The decision log is a rolling deque (capped at 10 entries) of completed decisions that is injected as text into the system prompt at the start of each new turn. This gives the agent lightweight recall of recent actions — analogous to a shift-change handover note — without the expense of full conversation replay.

This two-layer design is a deliberate tradeoff: it sacrifices perfect recall of earlier turns within a session in exchange for predictable token usage and simpler state management, which is appropriate for a demonstration system where session length is bounded.

3. Decision Logic and Behavior

3.1 How the agent decides which tools to call

The LLM backbone (Claude Haiku) selects tools based on its understanding of the user's query and the tool descriptions in the API schema. No explicit planning graph or hard-coded decision tree is used; tool selection is emergent from the model's language understanding. This allows the agent to handle novel phrasings and query combinations without requiring enumeration of all possible cases.

In practice, a typical routing query follows this tool sequence: (1) get_agent_status to confirm the vehicle is idle and has sufficient battery, (2) check_inventory to verify the destination zone has the requested goods, (3) find_safe_path to compute the route. The agent may call tools in a different order or add extra calls if the first results reveal unexpected conditions (e.g., vehicle is busy → agent checks for alternative vehicles).

3.2 Response to different input situations

SituationAgent behavior

Vehicle is charging or busy Reports vehicle unavailability; may suggest alternative vehicles after checking fleet status

Multiple simultaneous blockers (vehicle charging AND zone empty) Reports both issues; ordering of which is prioritised first varies across runs (known limitation — see §5)

3.3 System prompt and persona

The system prompt establishes the agent's identity, safety rules, and memory context. It explicitly lists the four safety invariants (avoid human safety zones without escalation; refuse to dispatch low-battery vehicles; note conflicts with busy vehicles; escalate when uncertain) as hard constraints. Embedding these rules in the system prompt rather than encoding them purely in Python ensures the LLM's natural language reasoning layer is aware of them, reducing the risk of the model finding creative workarounds that satisfy the letter of a code-level rule while violating its intent.

4. Safety, Reliability, and Transparency

4.1 Safeguards implemented

SafeguardImplementationPurpose
Human safety zone check Pre-dispatch Python function (_safety_check) runs BFS to detect if the natural path traverses any zone in HUMAN_SAFETY_ZONES; injects warning into tool result before the LLM-selected path is returned Prevents routing recommendations through zones where human workers are present without supervisor sign-off
Iteration cap MAX_TOOL_ITERATIONS = 6 enforced in the reasoning loop; auto-escalates and terminates if exceeded Prevents runaway tool-call loops from consuming unbounded API tokens and clock time
Decision logging Every completed turn is appended to AgentMemory.decision_log with timestamp, query summary, and outcome Provides an auditable record of agent actions within a session, supporting operator review
Low-battery rule Encoded in the system prompt; tool result for a charging vehicle includes battery percentage, which the LLM uses to apply the rule Prevents vehicles with critically low battery from being dispatched, avoiding mid-task breakdowns
Escalation tool Explicit tool with urgency levels ('low', 'medium', 'high', 'critical'); the model is instructed to call it proactively when uncertain Human-in-the-loop mechanism for decisions that exceed the agent's confidence or authority scope
Design principle — defence in depth: Safeguards are implemented at two layers: the Python _safety_check function (code-level, deterministic) and the system prompt rules (LLM-level, probabilistic). Neither layer alone is sufficient; the combination provides defence in depth against both code gaps and LLM reasoning failures.

4.2 Transparency mechanisms

The agent's reasoning is observable through two channels. First, the verbose logging mode (default: on) prints each tool call, its arguments, and its result to standard output as the reasoning loop executes. This allows a human observer to trace exactly how the agent arrived at its recommendation, step by step. Second, the decision log in AgentMemory records a summary of each completed decision and is re-injected into the system prompt, making the agent's recent history visible both to the LLM and to any human reviewing the session state.

Transparency is particularly important for agentic systems because the emergent tool-selection behavior of an LLM can be difficult to predict in advance (Wang et al., 2024). Making the reasoning trace explicit allows operators to identify when the agent's tool-call sequence deviates from expectations — for example, calling escalate_to_human for a query that seemed routine — which may indicate an edge case worth investigating or a system prompt ambiguity worth clarifying.

5. Observed Behavior and Limitations

5.1 Observed behavior across execution scenarios

Scenario 1 (normal routing): The agent correctly chained three tool calls in logical order — vehicle status, inventory check, path computation — and returned a clear recommendation that confirmed the vehicle's availability, the zone's inventory adequacy, and the specific route. No safeguards were triggered. This scenario demonstrates the baseline agentic behavior: the model decomposes a multi-faceted query into a sequence of atomic tool calls and synthesises the results into a coherent answer.

Scenario 2 (safety zone triggered): When asked to route AGV-1 from zone A to zone D — a path whose natural BFS solution traverses MAIN_AISLE — the pre-dispatch safety check correctly injected a warning into the tool result. The model received the warning and autonomously called escalate_to_human with urgency='high', generating an escalation ticket. The agent then communicated clearly to the manager that supervisor approval was required before the route could be authorised. This demonstrates the intended fail-safe behavior and the effectiveness of the two-layer safeguard design.

Scenario 3 (conflicting blockers — limitation observed): A request to dispatch AGV-2 (12% battery, charging) to zone B (zero inventory) exposed a prioritisation gap. The agent correctly identified both issues via tool calls, but the order in which it presented them in the final response was inconsistent across runs — sometimes leading with the battery warning, sometimes with the empty zone. This reveals that the system has no explicit conflict-resolution policy beyond what the LLM infers from the system prompt. For safety-critical systems, the order in which issues are surfaced matters: a battery failure mid-route is a different category of risk from an empty pick zone, and operators benefit from a consistent, prioritised presentation.

5.2 Known limitations

  • Static simulated state: All warehouse data (inventory, fleet, zone graph) is hardcoded in Python dicts. Real-world deployments would require live WMS API integration, which introduces latency, authentication, and failure handling complexity not addressed here.
  • No cross-session memory: The decision log and conversation history are in-memory structures that are lost when the notebook kernel is restarted. A production system would persist decisions to a database or log file.
  • No conflict-resolution priority policy: When multiple simultaneous blockers are present, the agent's presentation order is LLM-dependent and non-deterministic. Explicit priority rules (e.g., safety > availability > inventory) should be encoded in the system prompt or as a post-processing step.
  • LLM non-determinism: Even with temperature=0 (not set in this implementation), minor variation in LLM outputs means the agent's response to identical queries may differ between runs. This is acceptable for a demonstration system but must be addressed in production through deterministic fallback paths for safety-critical decisions.
  • BFS pathfinding simplicity: The zone graph is a coarse adjacency model. BFS finds the path with fewest zone transitions but ignores travel time, congestion, or vehicle-type traversal constraints. A production implementation would use a weighted graph with A* or a specialised logistics routing algorithm.

6. Ethical and Responsible Use Considerations

Primary ethical concern: accountability gap in partially autonomous decisions

The WIA agent is designed as a decision-support system, not a fully autonomous one: it recommends rather than executes, and it escalates rather than overrides when safety constraints are violated. However, the gap between recommendation and action is narrower than it may appear. In a time-pressured warehouse environment, a manager receiving a clear, confident routing recommendation from an AI system may follow it without independently verifying the tool results that underpinned it — particularly if the verbose log is not visible in the operational UI. This creates a subtle accountability gap: if the recommendation is wrong (e.g., due to stale inventory data or a BFS path that was technically valid but operationally inadvisable), the agent generated the decision, but a human implemented it. Responsibility for the outcome becomes ambiguous.

This pattern — where AI system design implicitly shifts moral responsibility from the system to the human operator — is a recognised ethical concern in autonomous AI deployment (Wang et al., 2024). The WIA system addresses this partially through its verbose reasoning trace and decision log, which make the agent's inference chain auditable. However, these mechanisms are only effective if operators are trained to consult them and organisational culture supports questioning AI recommendations. Technical safeguards alone are insufficient; responsible deployment requires complementary governance: clear documentation of system scope and limitations, operator training on when to override AI recommendations, and a defined escalation path for situations the system cannot resolve.

A second ethical concern is bias in safety zone coverage. The HUMAN_SAFETY_ZONES set is manually configured by the system designer. If this set is incomplete — because certain zones were not documented, or because the warehouse layout changed after deployment — the agent may recommend routes through areas that are de facto human zones, posing a physical safety risk. In a production context, safety zone data should be sourced from authoritative operational documentation and reviewed regularly, not hardcoded by a software developer. The system's current design makes the zone list a single point of failure that is invisible to the LLM unless it appears explicitly in the tool result.

7. Future Improvements

7.1 Persistent memory and cross-session continuity

Replacing the in-memory decision log with a persistent store (e.g., SQLite or Redis) would allow the agent to recall decisions from previous shifts. This would support pattern analysis — identifying recurring escalations that might indicate a systemic issue — and would give shift-change supervisors a structured handover briefing without manual note-taking.

7.2 Live WMS integration

Replacing the simulated tool implementations with real REST API calls to a Warehouse Management System would make the agent deployable in an actual logistics environment. This would require adding retry logic, timeout handling, authentication token management, and graceful degradation when APIs are unavailable — all of which are standard production engineering concerns absent from the demonstration implementation.

7.3 Explicit conflict-resolution policy

Adding a structured priority policy for competing blockers — encoded either as explicit rules in the system prompt or as a post-processing layer that sorts and formats the agent's findings before returning them — would eliminate the ordering inconsistency observed in Scenario 3 and make the agent's behavior more predictable for operators.

7.4 Formal evaluation harness

A systematic evaluation of agent behavior across a larger scenario battery — including adversarial inputs, edge cases, and degraded-state scenarios — would provide the quantitative reliability evidence needed for a production deployment case. This could build on the Reflexion framework (Shinn et al., 2023), where the agent's past failures are used to refine its system prompt and reasoning strategy iteratively.

7.5 Expanded safeguard coverage

Current safeguards focus on routing safety. Future work should add: rate-limiting for escalation calls (to prevent alert fatigue), audit logging to an external immutable store, input sanitisation to prevent prompt injection attacks against the LLM, and confidence scoring on tool results to flag when data quality is insufficient for a reliable recommendation.

7.6 Multi-agent extension

The single-agent WIA could be extended to a multi-agent architecture where specialised sub-agents (inventory analyst, route planner, vehicle scheduler) handle different aspects of a query in parallel, coordinated by an orchestrator agent. This aligns with the hierarchical multi-agent patterns explored in the broader capstone project on logistics fleet coordination and would be a natural next step toward a production-grade system.
